# FL-05 — Agent Concepts and MCP Basics

**Track:** General AI Fluency  
**Prepared:** 10 October 2026  
**Word count:** to be checked after save

## Explainer

An AI workflow and an AI agent can both use language models and tools, but they differ in who chooses the next step. In a workflow, the path is laid out in advance: step A hands a defined output to step B, then step C. The model may still make judgments inside each step, but the overall sequence is fixed. In an agent, the model has more control over the process. It observes a result, decides which action or tool to use next, checks what happened, and can repeat or change course until it reaches a stopping condition or needs a person. Tool access alone does not make a system an agent; the important question is whether the model dynamically directs the process or follows a predetermined path. Anthropic describes workflows as predefined code paths and agents as systems in which the model directs its process and tool use. It also recommends starting with the simplest pattern that works, because more autonomy can add cost and compound errors. ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents))

My FL-04 opportunity triage build is a workflow. A person supplies one opportunity URL; four prepared prompts gather evidence, compare it with a profile, critique the proposed decision, and format a brief. Each stage has a defined handoff and the next stage is known before the run starts. The critique step can catch errors, but it does not decide on its own whether to search again, which source to inspect next, or when to stop. That makes the pipeline a predictable prompt chain with a review stage, not an agent. The human still checks the employer’s live page and makes the final decision.

MCP, or Model Context Protocol, is an open standard for connecting an AI application to external data and capabilities. A host application can connect through an MCP client to one or more MCP servers. The protocol standardizes how those parts discover available capabilities and exchange requests and results; it does not decide how a model reasons or guarantee that a tool’s answer is correct. MCP uses JSON-RPC messages and can communicate through local standard input/output or remote Streamable HTTP, among other protocol details. The “USB-C for AI” comparison is useful for remembering that it standardizes the connection, not what the connected service does. ([MCP introduction](https://modelcontextprotocol.io/docs/getting-started/intro), [Architecture overview](https://modelcontextprotocol.io/docs/concepts/architecture))

The three server primitives have different jobs. **Tools** are callable functions, such as searching a job site, fetching a posting, or checking a deadline. They can read data or cause an action, so the client and server should make their inputs, effects, and permissions clear. **Resources** are addressable context, such as a document, a saved profile, a database record, or a source page. They let a client provide relevant data without turning every piece of context into an action. **Prompts** are reusable message templates, often with arguments, that a person can choose from a client interface. A prompt can standardize a triage request; it does not itself fetch the job listing. A server advertises the primitives it supports, and a client can present or call them according to their type. ([MCP architecture](https://modelcontextprotocol.io/docs/concepts/architecture), [Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [Resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources), [Prompts](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts))

A concrete agent upgrade for FL-04 would be a bounded “verify this opportunity” agent connected to a small, read-only MCP server. It could receive a search topic or job URL, call a search tool to find the employer’s official listing, fetch that page, and compare stated duties, eligibility, location, schedule, deadline, and pay with a profile resource. If a material field is missing or two official pages conflict, it could choose another approved source or ask the user a focused question. It would then produce the same evidence card and KEEP / REVIEW / SKIP brief as FL-04. The key change is that the model would choose the next permitted lookup based on what it found, rather than always executing the same four prompts.

The agent should have a small tool set, clear source rules, and a hard limit on searches or retries. It should treat job-page text as untrusted input, keep evidence links with claims, mark unknowns instead of filling gaps, and stop when a critical fact remains unresolved. The profile resource should expose only information needed for matching. The agent should have no tool for applying, emailing recruiters, or changing profile data. A person must verify the current posting and all eligibility facts before acting. This design adds flexible research while keeping the final decision and any consequential action with the human.
